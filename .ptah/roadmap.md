# Roadmap — Qaa El-Hamour

> Generated by saas-workspace-initializer (Stage A).
> Each unchecked item is a Stage B task. Run `/orchestrate <slug>` in a new chat session.

**Project.** An interactive React Three Fiber brand website themed on the viral Egyptian
trend "Qaa El-Hamour" — a scroll-driven camera dive through an underwater scene with
interactive landmarks standing in for portfolio sections. Built as a **config-driven
open-source template** others fork and deploy.

**Stack.** React + R3F + Vite in an Nx monorepo. Static-first hosting with exactly one
serverless seam (functions + Prisma/managed Postgres) serving the public complaints wall.
No auth code of our own. Single-tenant per deployment.

**MVP.** The dive plus two landmarks: the Pineapple (about) and the Complaints Bureau
(contact). The Tiki head and Krusty Krab are deliberately post-MVP.

See `.ptah/scope-decisions.md` for the full discovery record and the asset/IP constraints.

## Phase 1: Foundation

- [x] workspace-init: Nx workspace + web and api apps
      **Charter.** Bootstrap the Nx monorepo (npm workspaces, TypeScript project references), an `apps/web` React + Vite + R3F app, and an `apps/api` app holding a Fetch-API health handler only. Configure ESLint with `@nx/enforce-module-boundaries` across three tag dimensions — `scope:`, `type:`, `platform:` — plus Prettier, TypeScript strict mode, and Vitest. The workspace is the substrate every later item builds on, and the boundary rules are what keep the template forkable rather than tangled. Success: `nx run-many -t lint typecheck test build` passes on a clean clone, `nx graph` renders, and a deliberate cross-scope import fails lint.
      **Depends on:** none

- [x] shared-primitives: shared domain, util, and api-interfaces libraries
      **Charter.** Create `libs/shared/domain` (Result type, base value-object, branded-id helper), `libs/shared/util` (pure helpers), and `libs/shared/api-interfaces` (DTO contracts shared between `apps/web` and `apps/api`). Every bounded context imports these, and `api-interfaces` is the only type channel across the static/serverless boundary. Success: all three libraries build, carry correct tags, and are importable from both apps via `tsconfig.base.json` paths.
      **Depends on:** workspace-init

- [x] asset-manifest: World asset manifest and CC-BY attribution data
      **Charter.** Create `libs/world/domain` holding the `AssetManifest` contract (asset id, path, byte budget, quality tier availability) and the `Attribution` records for all four CC-BY-4.0 models. Attribution is a legal requirement of the licenses, not a nicety, so it lives as typed data next to the manifest it describes and cannot drift from the assets it covers. Every 3D roadmap item consumes this contract. Success: the manifest type-checks, lists all four bundled models with their required credit strings, and `apps/web` imports it.
      **Depends on:** shared-primitives

- [x] ci-baseline: Lint, typecheck, and test on pull request
      **Charter.** Add a GitHub Actions workflow running `nx affected -t lint,typecheck,test` on pull requests, with npm caching and the Nx SHA setup action. No deploy job yet — deployment lands in Phase 7. This is the guard that keeps a multi-session Stage B from silently regressing earlier phases. Success: the workflow runs green on a pull request against a clean clone.
      **Depends on:** workspace-init

## Phase 2: Asset Pipeline

- [x] asset-audit: Inventory the bundled models and locate missing landmarks
      **Charter.** Open the four bundled glTF files and catalogue what geometry actually exists: node names, mesh counts, triangle budgets, texture sets, and material types. The blueprint calls for four landmarks but only the Pineapple exists standalone — this item determines whether the Tiki head and Krusty Krab can be extracted as sub-meshes from `bikini_bottom_map_3d_model` or must be sourced separately, which is a hard prerequisite for scoping Phase 4's post-MVP landmarks. Success: a written inventory in `docs/asset-inventory.md` naming the extractable node for each of the four landmarks, or flagging it as missing with a sourcing recommendation.
      **Depends on:** asset-manifest

- [x] asset-compression: Draco/Meshopt geometry and KTX2 texture pipeline
      **Outcome.** `npm run assets:compress` / `assets:verify` (`tools/asset-pipeline/`); 8 committed outputs, initial load 1,272 KiB of a 1,800 KiB budget. Textures shipped as WebP (KTX-Software not installable here — switch documented). Outputs verified by decode in Node, not yet in the R3F scene: first in-scene load belongs to `world-environment`. Reviews and open minors: `.ptah/specs/asset-compression/`.
      **Charter.** Build a repeatable `tools/` script that compresses source models into web-ready assets: Meshopt or Draco for geometry, KTX2/Basis for textures, with per-asset output recorded against the manifest's byte budget. The raw assets total 27.6 MB — the SpongeBob model alone is 17 MB — which is far past any usable first-load budget, so this is a hard prerequisite for rendering anything real rather than an optimization pass. Success: the script runs from a clean checkout, total compressed payload for MVP landmarks lands under an agreed budget, and outputs load correctly in `apps/web`.
      **Depends on:** asset-manifest, asset-audit

- [ ] asset-attribution-ui: In-world credits plaque
      **Charter.** Render the CC-BY-4.0 attribution for all four models as a visible in-world element — a municipal notice board or credits plaque that fits the art direction instead of fighting it — driven entirely by the `Attribution` records from `asset-manifest`. The licenses require visible credit, so shipping without this is a license violation, and hard-coding the text would let it drift from the assets. Success: every bundled model's required credit string is reachable from the live site, and adding a model to the manifest adds its credit automatically.
      **Depends on:** asset-manifest

## Phase 3: The Dive

- [x] world-environment: Underwater environment and shaders
      **Outcome.** `libs/world/feature`: `<OceanWorld>` with fog, procedural caustics patched into map materials, GPU-animated plankton/bubbles, light rig, error-bounded model load, bounded orbit controls. World-scale convention: `WORLD_SCALE = 20`, single-sourced via `WorldScaleProvider`/`useSceneToWorld` — landmarks sit in raw scene-world units inside `<WorldSpace>`. 60 FPS measured on an RTX 3070 laptop only; mid-tier reading still owed (quality-tiers). Open minors: `.ptah/specs/world-environment/code-logic-review-glm-r2.md` #2–4; `OceanWorld` children need their own `<Suspense>`.
      **Charter.** Create `libs/world/feature` with the R3F components that make the scene read as deep ocean: exponential fog, a caustics projection on the ocean floor, an instanced bubble/plankton particle system, and the ambient light rig. This is the atmosphere the entire site trades on — if the water does not feel deep and murky, no landmark work will save it. Success: `apps/web` renders a navigable underwater scene holding 60 FPS on a mid-tier laptop with no landmarks present.
      **Depends on:** asset-compression

- [ ] dive-camera: Scroll-driven CatmullRom camera path
      **Charter.** Create `libs/dive/{domain,feature}` implementing the dive: a `DivePath` value object over a CatmullRom spline, waypoints per landmark, and a scroll-bound camera controller that eases along the curve. The dive is the site's core navigation metaphor and the single interaction every visitor performs, so its feel is the difference between memorable and gimmicky. Success: scrolling moves the camera smoothly down the spline, depth state is observable, and the path is defined by data rather than hardcoded coordinates.
      **Depends on:** world-environment

- [ ] quality-tiers: Adaptive quality and device tiering
      **Charter.** Detect device capability and sustained frame rate, then select a quality tier that gates particle counts, postprocessing, texture resolution, and shadow use — wired to the tier field already present in the asset manifest. A WebGL site that stutters on mid-range Android is unusable for the largely mobile Egyptian audience this trend belongs to. Success: the scene degrades measurably on a throttled device and holds an acceptable frame rate at every tier.
      **Depends on:** world-environment

## Phase 4: Landmarks & Content

- [ ] landmark-kernel: Reusable landmark abstraction
      **Charter.** Create `libs/landmarks/{domain,feature,ui}` defining what a landmark *is*: a positioned model with a hit target, hover and focus states, a camera-focus transition, and a bound HTML overlay. This is the template's single most important abstraction — four landmarks ship and forkers will add their own, so the abstraction must make a new landmark a data entry plus an overlay component, never a scene-graph edit. Success: a landmark is declarable from data, and adding one requires no change to `libs/dive` or `libs/world`.
      **Depends on:** dive-camera

- [x] content-model: Content domain and CMS-backed data access
      **Outcome.** `libs/content/{domain,data-access}` + `content/` workspace package (`@qa3elhamor/content-files`): SiteProfile, ResumeEntry, ServiceItem, ProjectItem, Credit; inline `{ en; ar? }` localisation; `nx build web` depends on `content-data-access:validate`, so invalid content cannot deploy. Ships SAMPLE content for a fictional "Your Name" — the owner's real content replaces it.
      **Charter.** Create `libs/content/{domain,data-access}` modelling `SiteProfile`, `ResumeEntry`, `ServiceItem`, and `Credit`, loaded from CMS-generated JSON at build time. Content must be fully data-driven for the template goal — a forker changes content files and nothing else — and the strict scope boundary means landmarks never import this library directly. Success: all site copy resolves from content files, and `apps/web` wires content into landmarks as props.
      **Depends on:** shared-primitives

- [ ] landmark-pineapple: About landmark and Citizenship Card overlay
      **Charter.** Place the Pineapple house as the first MVP landmark, opening a "Citizenship Card for Qaa El-Hamour" overlay carrying the bio and skills, rendered from `content-model` data. This is one half of the MVP and the first end-to-end proof that the kernel, content model, and dive compose correctly. Success: diving to the Pineapple and clicking it opens a content-driven overlay, and returning to the dive restores camera state cleanly.
      **Depends on:** landmark-kernel, content-model

- [ ] landmark-bureau: Contact landmark and complaint scroll overlay
      **Charter.** Build the Municipal Complaints Bureau as the second MVP landmark: an underwater booth whose click floats up a paper-scroll contact form with subject, complaint body, and sender name/species, submitted under a Sardine Municipal Stamp. This completes the MVP and is the site's only conversion point, turning the trend's central motif into the call to action. Success: the form validates and renders correctly; actual delivery is wired in `complaints-contact-adapter`.
      **Depends on:** landmark-kernel, content-model

- [ ] cms-integration: Git-based CMS wiring
      **Charter.** Wire a Git-based CMS (Decap or Tina) so content edits commit to the repository and trigger a rebuild, with schemas matching the `content-model` types. The CMS provider owns its own authentication, which is what lets the site keep zero auth code while still satisfying the editable-content requirement. Success: editing the bio through the CMS UI produces a commit and a redeployed site with no code change.
      **Depends on:** content-model

- [ ] landmark-tiki: Resume landmark (post-MVP)
      **Charter.** Add Squidward's Tiki head as the resume landmark, presenting chronological experience as grumpy "Performance Reviews" from past managers. Deliberately post-MVP: it is a repetition of the kernel proven by the two MVP landmarks, not new invention. Success: the resume renders from `content-model` entries with no change to `landmark-kernel`.
      **Depends on:** landmark-pineapple, asset-audit

- [ ] landmark-krusty-krab: Services landmark (post-MVP)
      **Charter.** Add the Krusty Krab with a 3D menu board presenting services as menu items — Kelp Shake, Classic Krabby Patty, Secret Formula — that zoom on hover. Post-MVP for the same reason as the Tiki head. Success: services render from `ServiceItem` content entries and the hover-zoom reads clearly on mobile.
      **Depends on:** landmark-pineapple, asset-audit

## Phase 5: Complaints

- [x] complaints-domain: Complaint aggregate and moderation states
      **Outcome.** `libs/complaints/domain`: visibility-split `Complaint` aggregate (private: submitted→delivered/failed; public: pending→approved/rejected→deleted), UGC validation after normalisation, clock injection, `restoreComplaint(unknown)` treats storage as untrusted. 197 tests.
      **Charter.** Create `libs/complaints/domain` with the `Complaint` aggregate, its `Visibility` (private routes to the owner's inbox, public routes to the wall), and its moderation lifecycle. Modelling contact and the wall as one aggregate with two visibilities is the domain insight of this project — the trend's own metaphor is that everything is a complaint filed with the municipality. Success: the aggregate enforces valid state transitions and is shared by both the static and serverless paths.
      **Depends on:** shared-primitives

- [ ] complaints-contact-adapter: Private complaint delivery
      **Charter.** Wire private complaints from the Bureau form to a serverless-free form service (Web3Forms or Formspree) behind an adapter interface, so the static path stays static. Deliverability is the whole point of a contact form, and the adapter keeps the provider swappable for forkers who prefer another service. Success: submitting the Bureau form delivers a real message, and swapping providers requires only an env var and one adapter file.
      **Depends on:** complaints-domain, landmark-bureau

- [ ] complaints-api: Serverless wall endpoints with Prisma
      **Charter.** Build the project's only backend seam in `apps/api` plus `libs/complaints/{data-access,feature-api}`: Prisma schema and migrations against a managed Postgres, and three handlers — submit a public complaint, list approved complaints, and a token-protected moderation route. Rate limiting and input validation ship with it, because an unauthenticated public write endpoint is the site's entire attack surface. Success: the three endpoints work against a real database, abusive submission rates are rejected, and the site still builds and deploys with the database absent.
      **Depends on:** complaints-domain

- [ ] complaints-wall: In-world public complaints wall
      **Charter.** Render approved public complaints as an in-world board — a municipal notice wall visitors dive past and can post to — reading from `complaints-api`. This is the feature that makes the site participatory rather than a portfolio, mirroring the Facebook group the trend actually was. Success: a visitor posts a complaint, sees it enter moderation, and approved complaints appear on the wall for everyone.
      **Depends on:** complaints-api, landmark-kernel

- [ ] complaints-moderation: Moderation surface
      **Charter.** Provide a minimal moderation view behind the shared-secret token — list pending complaints, approve, reject, delete — with no user system. Public UGC without moderation is an unacceptable liability for a site carrying the owner's name and brand. Success: a pending complaint can be approved or rejected from the surface, and an invalid token returns 401.
      **Depends on:** complaints-api

## Phase 6: Telemetry & Template Readiness

- [ ] telemetry-events: Dive and engagement analytics
      **Charter.** Create `libs/telemetry/{domain,data-access}` dispatching cookieless events to a hosted provider (Plausible or Umami): dive depth reached, landmark clicks, overlay opens, drop-off point, and resolved quality tier. Cookieless keeps the site clear of consent banners, and dive-depth data is the only way to know whether visitors actually reach the deeper landmarks. Success: events land in the provider dashboard and no analytics cookie is set.
      **Depends on:** dive-camera

- [ ] template-config: Forkability pass
      **Charter.** Audit and close the gap between "our site" and "a template": every string, colour, asset path, landmark position, and provider key resolves from config, with a documented swap procedure and a working example of replacing a landmark model. The template framing was the primary audience answer in discovery, so this item is where that answer is actually cashed in rather than assumed. Success: a fresh clone can be rebranded end to end by editing config and assets only, verified by doing it.
      **Depends on:** landmark-pineapple, landmark-bureau, content-model

- [ ] i18n-bilingual: Arabic and English with RTL
      **Charter.** Add bilingual content support with correct RTL layout for Arabic overlays, since the trend is Egyptian and much of its comedy — "بقينا في القاع", the Sardine President — only lands in Arabic. Success: switching locale flips overlay direction correctly and both locales render from the same content entries.
      **Depends on:** content-model

## Phase 7: Deployment & Hardening

- [ ] deploy-static: Static hosting with serverless functions
      **Charter.** Deploy `apps/web` as a static bundle with `apps/api` as co-located serverless functions on Vercel or Netlify, including long-lived immutable cache headers for compressed 3D assets and correct MIME handling for KTX2 and glTF binaries. Asset caching is disproportionately important here because the payload is dominated by a handful of large binary files. Success: a merge to `main` produces a live deployment and repeat visits serve assets from cache.
      **Depends on:** template-config

- [ ] perf-budget: Enforced first-load budget in CI
      **Charter.** Add CI gates that fail a pull request exceeding agreed JavaScript-bundle and total-asset budgets, plus a Lighthouse run on the deployed preview. A 3D site's payload creeps upward with every landmark, and without an enforced gate the mobile experience degrades invisibly across Stage B sessions. Success: an artificially oversized asset fails CI with a clear message.
      **Depends on:** asset-compression, deploy-static

- [ ] security-hardening: CSP, validation, and abuse limits
      **Charter.** Apply a Content Security Policy compatible with WebGL and the analytics provider, strict server-side validation and length limits on wall submissions, output escaping for user-authored complaint text, and abuse rate limiting beyond the basic pass in `complaints-api`. The wall accepts unauthenticated public input and renders it to every visitor, making stored XSS the single highest-severity risk in the project. Success: a security review of the wall path passes with no high or critical findings.
      **Depends on:** complaints-api, deploy-static

## Phase 8: QA & Launch

- [ ] a11y-fallback: Reduced motion and non-WebGL fallback
      **Charter.** Provide a genuine alternative path: honour `prefers-reduced-motion` by disabling the dive animation, and serve a readable 2D version of all content to visitors without WebGL or on failing hardware. A site whose only navigation is a scroll-driven 3D dive excludes people with vestibular sensitivity and anyone on unsupported hardware, and the content is a portfolio those visitors still need. Success: every piece of site content is reachable with WebGL disabled.
      **Depends on:** landmark-pineapple, landmark-bureau

- [ ] qa-smoke: End-to-end smoke and visual regression
      **Charter.** Add Playwright coverage of the critical paths — dive to each landmark, open each overlay, submit a private complaint, post to the wall — plus screenshot comparison on the canvas at a fixed camera position to catch shader and asset regressions. Canvas rendering is invisible to conventional assertions, so without visual regression a broken material ships silently. Success: the suite runs green in CI against a preview deployment.
      **Depends on:** deploy-static, complaints-wall

- [ ] launch-checklist: Public launch and template release
      **Charter.** Final pass before going public: verify all four CC-BY credits render, confirm the branding leans on the Egyptian trend framing rather than SpongeBob IP per the scope decisions, write the fork-and-deploy README, add a LICENSE, and prepare the repository for public release. This is where the IP-exposure judgement recorded in discovery gets actually applied rather than remaining a note. Success: the repository is public, a fresh fork deploys successfully by following the README alone.
      **Depends on:** qa-smoke, a11y-fallback, asset-attribution-ui, perf-budget, security-hardening
